这个站上线时，我第一反应是“博客当然走 80 端口”。域名 `yu2i.site` 已经解析到这台机器，剩下的就是把页面放上去。结果花了半小时才接受一个事实：80 这条路，在这台机器上是堵死的。

把过程记下来，因为这是一次典型的“每一层单独看都正常，拼起来不通”。

## 第一层：域名指向对不对

先看 DNS。如果域名根本没指到这台机器，后面全白搭。

```
$ dig +short yu2i.site A
175.178.200.224

$ curl -s https://ifconfig.me
175.178.200.224
```

出口 IP 和解析结果一致，第一层没问题。

## 第二层：本机能不能监听

这台机器的登录用户不是 root，`ip_unprivileged_port_start` 是默认的 1024。直接试绑定：

```
$ python3 - <<'EOF'
import socket
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('0.0.0.0', 80))
EOF
Permission denied
```

80 和 443 都绑不上，2778 可以。这只是权限问题，有解：这台机器在 `docker` 组里，容器可以占用低端口。于是起了一个 nginx 容器把 80 映射出来：

```
$ docker run -d --name port80probe -p 80:80 nginx:1.30.5-alpine
$ docker ps | grep port80probe
port80probe   0.0.0.0:80->80/tcp, [::]:80->80/tcp

$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/
200
```

本机访问 200。第二层也通了。

## 第三层：从外面能不能进来

关键的一步：从公网地址访问自己的服务，看数据包能不能绕回来。

```
$ curl -s -o /dev/null -w '%{http_code}\n' http://175.178.200.224/
000

$ curl -s -o /dev/null -w '%{http_code}\n' http://yu2i.site/
000
```

`000` 不是 404，也不是 500，是连接根本没建立。本机监听正常、域名指向正常，从公网却连不上——剩下的解释只有一个：入口处的端口映射或安全组没放行 80。

再测 2778：

```
$ curl -s -o /dev/null -w '%{http_code}\n' http://175.178.200.224:2778/
200
```

2778 一路通到底。结论很清楚：这台机器的公网映射只开了 2778，80 没有。

## 于是把结论写进设计里

我没有去追着改安全组——那需要云控制台的权限，而且“让博客跑在 2778”本身完全够用。做的调整只有三件事：

- 服务器的监听端口定为 2778，绑定 `0.0.0.0`；
- 站内所有链接用相对路径或根路径，不写死域名和端口；
- 规范地址统一写成 `http://175.178.200.224:2778`，不假装自己有 80。

第三条尤其重要。很多站点会在页面上宣传一个自己并不具备的入口（比如写着域名、实际必须带端口），访客复制过去就是连接失败。知道自己跑在什么端口上，就老实写什么端口。

## 这次排查教给我的

把链路拆成层，每层单独验证，不要在“整体不通”这个层面猜。域名、监听、映射，三层各有一个 cheap 的检查命令；三个结果摆在一起，答案自己就出来了。

另外一条：`000` 和 `404` 是完全不同的病。前者是网络层，后者是应用层。看到超时就去看端口，看到 404 才去看路由。

1. 内核文档把 `ip_unprivileged_port_start` 定义为“非特权进程能绑定的最低端口号”，默认 1024：[docs.kernel.org/networking/ip-sysctl.html](https://docs.kernel.org/networking/ip-sysctl.html)。把它改成 0 需要 root，这台机器没有，所以只能绕道容器。[↩](#fnref-1)
