建这个站的时候，最省事的路径本来是装一个博客框架：写 Markdown、跑一条构建命令、主题挑一个、部署到某个平台。十分钟能出活。我没有那么做。

> 2026-11-10 补记：这段结论后来被推翻了。站还是换成了 Astro，理由写在[《这个站为什么又开始重建了》](/posts/rebuild-again/)。这篇保留原文，不改。

不是反对框架。是这笔账在这个场景里算不过来。

## 一、内容的增长单位是“篇”，不是“万”

博客框架的价值建立在规模上：几百上千篇文章、多作者、标签系统、全文检索、评论、RSS 聚合、增量构建。这些东西在没有规模的时候全是空转。

一个人的博客，一年写二十篇算勤快。二十个页面的站点，目录结构用手都能记住。为了管理二十个页面去引入一个需要 Node 版本、依赖锁文件、构建产物和部署流水线的系统，是在用工业流水线烤一块面包。

## 二、依赖会过期，HTML 不会

这是我最在意的一条。框架版本一年半载就断代一次，主题跟着断，插件跟着断。三年后想改一行页脚，先得把整条工具链从旧版本里刨出来。

而这个站的构成是：

- 十来个 `.html` 文件；
- 一个 CSS 文件，一个 2 KB 的 JS 文件，一个 SVG 图标；
- 一个一百多行的 Python 服务器。

十年后打开任何一个浏览器，它仍然能显示。没有任何一步需要“先安装环境”。

## 三、手写才能控制那 5%

框架给的是 95% 的默认正确：响应式、无障碍、SEO、图片处理。剩下 5% 是让一个站点不像是模板生成的部分——字号的比例、行距的松紧、留白的节奏、hover 时位移的距离。这些恰恰是框架最难改的地方，因为它们散落在主题的几十个文件里。

手写 CSS 意味着我可以为一个标题单独定 `clamp(2.6rem, 7.2vw, 5.4rem)` 的字号，可以让文章列表的行在鼠标悬停时右移 4 像素而不是变色，可以让中文正文的行高到 2.05 而不是常见的 1.6。这些细节单独看都不重要，堆在一起就是“这个站有人管过”和“这个站是装出来的”的区别。

框架解决的是“多人协作、高频发布、规模增长”。个人博客三样都不占。

## 代价是什么

诚实一点，手写也有明显的代价：

| 代价 | 我的处理 |
| --- | --- |
| 每篇文章都要复制一遍页面骨架 | 骨架固定为一份，改版时用脚本批量替换；文章数量没到需要模板引擎的程度 |
| 没有自动生成的 RSS、站点地图 | 手写一份 `sitemap.xml`，文章少，改得动 |
| 没有图片优化流水线 | 这个站目前不放照片，放弃这个问题 |
| 写错一个标签没人拦 | 用浏览器打开看，肉眼验收 |
这些代价都能接受，因为量小。量一旦变大，结论就会反过来——那时候我会去装框架，而不是硬扛。

## 具体数字

整站体积（不含文章里的文字）：首页 HTML 约 11 KB，CSS 约 32 KB，JS 约 6 KB，图标 0.26 KB。首屏一次请求四个文件，没有第三方域名。服务器端 gzip 之后 HTML 约 3.8 KB、CSS 约 6.8 KB，JS 目前是原样下发的 6 KB——那颗压缩开关还没补上，首屏合计约 20 KB。

这个数字不是炫耀。它只说明一件事：在这个规模上，框架能带来的收益，小于它带来的复杂度。
